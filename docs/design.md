# Design notes

## The question is about patterns, not files

A glob matcher answers "does this pattern cover this path". That is the wrong
question for parallel work, because the answer is only available once the path
exists, and by then both lanes have written it.

The question here is: **can these two patterns ever name the same path?** That
is a language-intersection question, and it has an answer on day zero.

## Two levels of automaton

A pattern compiles to a list of path segments.

- A solitary `**` segment is an epsilon-skippable self-loop that consumes any
  one segment, so it matches zero or more whole segments.
- Every other segment consumes exactly one path segment, subject to a
  **segment-level** automaton over characters: `*` is a self-loop consuming any
  character, `?` consumes exactly one, a literal consumes itself.

Intersection is the product of two such automata, searched breadth-first. The
first accepting state reached yields the **shortest** word both accept, which
becomes the witness path. Shortest-first is what makes the witness a function of
the two patterns alone, and therefore deterministic.

At the segment level, the joint transition out of a pair of positions is
decided by what both sides allow: two literals must agree, one literal fixes the
character, and two wildcards take a filler character. Any character would do for
the filler; it never appears in the report except inside a witness that both
patterns genuinely match.

### The empty-word trap

Both searches carry a third state component: whether anything has been consumed
yet. Without it, `*` against `*` reports *disjoint*. The accepting state is
reached first by the empty word, gets marked visited, and is never reached again
with a real word — so the search finishes having found only a word that is not a
legal path segment, and concludes there is no overlap.

Two patterns that share only the empty word share no path, so the empty word has
to be rejected; but rejecting it must not poison the state it arrives at. The
consumed flag does both.

## Matching reuses the same engine

`matchesPath` compiles the concrete path into all-literal segments and
intersects. One code path means the matcher and the overlap detector can never
disagree about what a pattern means — and a disagreement there is exactly what
would let a change slip past the lane that owns it.

## What the engine refuses

Negation, character classes, extended globs, backslash escapes, absolute
patterns, a trailing `/`, and `**` inside a larger segment. Each of these is
refused rather than approximated.

The reason is narrow: the whole value of this tool is the *negative* answer.
"These lanes are disjoint" is what lets three agents start work in parallel. A
matcher that silently reads `**.js` as `*.js`, or drops a leading `!`, gives
that answer about a different pair of patterns from the ones it was handed. So a
pattern the engine does not implement makes the run incomplete, exits 2, and
says which pattern and what to write instead.

## Bounds, and the third answer

Every search is bounded. A search that reaches its bound does not return
"disjoint" — it returns `{ resolved: false }`, and the caller records the pair as
undetermined, emits `overlap-unresolved`, marks the report incomplete and
withdraws the merge order.

That third answer is the point. The bound exists so a pathological pattern pair
cannot hang the run; if hitting it were reported as "no overlap", the bound
would have converted a resource limit into a wrong green.

The same applies to the time budget. It is checked before the pair loop and at
every comparison boundary, and the clock it reads is injected as a default
parameter, so a test can step it past the deadline without waiting.

## Shared artifacts and the integration owner

A generated file is not owned by a lane; it is regenerated by one. The model:

- `sharedArtifacts` lists globs for files nobody authors by hand.
- `integrationOwner` names the single lane responsible for regenerating them.
- Two or more lanes changing a shared artifact with **no** integration owner is
  an error: at merge time nobody is responsible and the conflict is an
  unreadable diff.
- With an integration owner it is a warning that names the sequencing:
  regenerate once, in that lane, after the others merge.
- A lane other than the integration owner claiming a shared artifact in `owns`
  is an error, because ownership and the shared designation contradict.

Dependency lockfiles get a rule of their own by basename. They are the file two
lanes collide on most often and least expect to, because nobody edits one
deliberately — and the usual mistake is forgetting to declare it shared at all,
which is precisely the case the `sharedArtifacts` rules cannot see.

## What is not here

No git. The tool reads one JSON document and nothing else — no repository
enumeration, no branch inspection, no subprocess. That keeps it deterministic
(the same document is the same subject anywhere) and keeps its read set to
exactly one file, which is what makes the `--out` guard's input list complete
and checkable.
